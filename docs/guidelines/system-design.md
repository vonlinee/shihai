# 识海古诗词学习平台系统设计

## 1. 文档定位

本文档描述仓库当前可以从代码、依赖、配置和路由中确认的系统结构。产品目标和规划范围见 [需求设计文档](requirements-design.md)，编码细节见前后端专项规范。

本文档不是完整数据库字典或 OpenAPI 文档。字段和约束优先以当前 GORM 模型及实际路由为准；历史迁移脚本存在差异时，应先核实运行环境再修改。

## 2. 系统边界

识海当前由三个主要部分组成：

- `frontend/`：React 单页应用，提供公开页面和后台管理界面。
- `backend/`：Go HTTP 服务，提供认证、诗词、评论、公告、作品集、简繁转换和 RBAC 接口。
- `database/`：PostgreSQL 初始化和权限迁移脚本。

系统采用前后端分离架构。前端不能直接访问数据库，所有持久化操作都必须经过后端接口。

## 3. 当前技术栈

### 3.1 前端

- React 18、TypeScript 5、Vite 5。
- React Router 管理页面路由和懒加载。
- TanStack Query 管理服务端状态。
- Zustand 管理登录用户、主题等客户端状态。
- Axios 或 Fetch 通过统一 `HttpClient` 抽象访问后端。
- Tailwind CSS、Radix UI、lucide-react 提供样式和组件能力。

### 3.2 后端

- Go 1.21、Gin、GORM、PostgreSQL。
- `golang-jwt/jwt/v5` 负责 JWT 认证。
- `bcrypt` 负责密码哈希。
- Snowflake 生成业务主键。
- `longbridgeapp/opencc` 提供简繁文本转换。

### 3.3 当前未使用的规划依赖

配置结构中保留了 Redis 字段，但当前 `go.mod` 和业务代码没有 Redis 客户端或缓存读写。消息推送、敏感词服务和实时通知也没有形成可运行模块，因此只能视为规划能力。

## 4. 目录与模块

### 4.1 前端模块

```text
frontend/src/
├── components/  # 基础组件、布局和业务组件
├── hooks/       # 数据请求和业务 Hooks
├── pages/       # 公开页面与后台页面
├── services/    # HttpClient 和业务 API 封装
├── stores/      # Zustand 状态
├── types/       # 共享 TypeScript 类型
├── utils/       # 通用工具
├── router.tsx   # 路由配置
└── main.tsx     # 应用入口
```

公开路由包括首页、诗词列表、诗词详情、登录、注册和个人中心。论坛、问答页面目前只有页面入口，不代表对应后端业务已经完成。

后台路由包括仪表盘、用户、诗词、作品集、评论和纠错页面。页面是否存在与接口是否完整是两个独立状态，不能仅根据前端菜单判断功能已经交付。

### 4.2 后端模块

```text
backend/
├── cmd/server/          # 启动、依赖组装和路由注册
├── internal/config/     # 配置加载、数据库连接和 AutoMigrate
├── internal/database/   # 数据库初始化辅助能力
├── internal/dto/        # 请求和响应契约
├── internal/handlers/   # HTTP 适配
├── internal/middleware/ # JWT 与 RBAC 中间件
├── internal/models/     # GORM 模型、角色和权限码
├── internal/repository/ # 数据访问
├── internal/services/   # 业务规则和流程编排
└── pkg/utils/           # 响应、ID 等通用工具
```

当前启动容器实际组装的业务模块包括：

- 用户与认证。
- 诗词、朝代、作者或诗人、诗词标注。
- 评论与评论投票。
- 公告。
- 作品集。
- 简繁文本转换。
- 角色、权限和用户角色关联。
- 纠错后台列表查询。

论坛和问答已有模型或页面入口，但没有被组装为完整 Handler、Service、Repository 和路由链路。纠错目前已接入后台列表查询，审核、投票、应用修改和通知流程仍属于部分实现。

## 5. 请求链路

典型请求按以下方向流动：

```text
浏览器
  -> React 页面或业务组件
  -> TanStack Query Hook
  -> Service / HttpClient
  -> Gin 路由与中间件
  -> Handler
  -> Service
  -> Repository
  -> GORM / PostgreSQL
```

- Handler 负责请求绑定、HTTP 状态和响应封装。
- Service 负责业务规则和跨仓储流程编排。
- Repository 封装持久化查询和写入。
- DTO 是前后端接口契约，不能以数据库 Model 代替外部响应。

当前 API 统一挂载在 `/api`，没有 `/api/v1` 版本前缀。若引入版本化路由，必须同步更新后端路由、前端 Service 和接口文档。

## 6. 认证与权限

### 6.1 认证

登录成功后，服务端签发 JWT。受保护接口从 `Authorization: Bearer <token>` 读取令牌，由认证中间件解析用户 ID。

密码使用 bcrypt 哈希存储。密码、JWT 密钥和令牌不得写入响应或日志。

### 6.2 RBAC

当前默认角色为：

- `admin`：获取全部已注册权限。
- `editor`：内容编辑和相关管理权限。
- `reviewer`：审核相关权限。
- `user`：普通用户基础权限。

用户可以关联多个角色，最终权限为角色权限并集。权限码按 `模块:操作` 组织，路由通过 RBAC 中间件声明所需权限。

### 6.3 前后台权限边界

前端根据角色或权限控制菜单、按钮和页面提示，只用于改善交互体验。真正的访问控制必须由后端中间件执行；隐藏菜单不能替代授权。

后台 `/api/admin` 路由当前先要求 `admin` 或 `editor` 角色，再对具体接口检查权限。新增后台能力时必须同时评估角色入口限制和权限码，避免拥有权限但被角色门槛拒绝，或拥有角色却绕过具体权限。

## 7. 数据设计

### 7.1 当前模型关系

- 用户通过 `user_role` 关联角色，角色通过 `role_permission` 关联权限码。
- 诗词关联作者、朝代、正文范围标注、评论和作品集条目。
- 评论可以关联登录用户或游客标识，并通过 `parent_id` 形成回复关系。
- 评论投票关联评论以及登录用户或游客标识。
- 公告和后台资源使用统一基础模型字段。
- 论坛、问答、纠错模型已经存在；其中纠错只完成后台列表查询，完整审核链路仍属于部分实现。

多数业务模型内嵌 `BaseModel`，使用 Snowflake `uint64` 主键、创建更新时间、软删除和审计用户字段。对外返回雪花 ID 时应使用字符串，避免 JavaScript 数字精度丢失。

### 7.2 模型与迁移的已知差异

服务启动时会执行 GORM AutoMigrate。`database/migrations/001_init.sql` 是较早的初始化脚本，其中包含复数表名、`SERIAL` 主键和旧字段结构，与当前单数表名和 Snowflake 主键模型不完全一致。

因此：

1. 不得同时把旧迁移和当前模型视为同一版本的权威定义。
2. 修改数据结构前必须确认目标环境是依赖 AutoMigrate 还是迁移脚本。
3. 后续应通过独立任务统一迁移策略；本次文档重构不修改数据库行为。

## 8. 配置与运行

后端先按以下顺序选择一个配置文件路径：

1. `-config` 命令行参数指定的 JSON 文件。
2. `CONFIG_FILE` 环境变量指定的 JSON 文件。
3. 工作目录下的 `config.json`。
如果最终选中的文件不存在，则保留代码默认值，不再继续尝试下一条候选路径。文件处理完成后再应用环境变量覆盖。

数据库、服务端口、Gin 模式、Redis 占位配置和 JWT 配置结构都可以通过环境变量覆盖。环境变量优先于文件内容。

当前启动流程没有把加载后的 `JWT_SECRET` 和 `JWT_EXPIRES_IN` 传入 `pkg/utils` 的 JWT 实现，后者仍使用包内默认密钥和固定有效期。因此环境变量目前只改变配置结构，不能视为已经控制实际签名行为。公开部署前必须先修复这条接线并增加配置生效测试。

默认配置只适合本地开发，不应直接用于公开部署。

前端开发服务器默认使用 `3000` 端口，并将 `/api` 代理到 `VITE_BACKEND_URL`；未设置时使用 `http://localhost:8080`。

## 9. 后台管理模块

当前后端已注册的后台能力包括：

- 用户列表、详情、创建和删除。
- 角色、权限、角色授权和用户角色分配。
- 诗词、朝代、诗人和诗词标注管理。
- 作品集及作品集条目管理。
- 公告管理。
- 评论管理列表。
- 纠错管理列表。
- 批量文本简繁转换。

后台纠错页面目前接入真实列表数据，但没有对应的完整审核、投票和应用修改路由。论坛和问答也没有后台业务路由。导航或权限码存在不等于模块已经完成。

## 10. 安全边界与已知差异

- 当前 CORS 中间件允许任意来源，生产部署前需要按实际域名收紧。
- 当前服务启动逻辑包含默认管理员账号和固定初始密码，生产部署前必须改为安全初始化流程。
- 评论投票在缺少 `X-Visitor-ID` 时存在直接使用客户端 IP 作为游客标识的回退路径。这不满足需求文档中的随机、不透明标识目标，也不能被描述为已完成匿名化。
- 配置默认值包含开发数据库凭证；JWT 配置尚未接入实际签名工具，不能仅靠设置环境变量解决默认密钥问题。
- 当前用户模型和部分前端共享类型仍保留年龄、手机号、身份证号或登录角色等历史字段，与最新需求基线不完全一致；新增流程不得继续扩大这些字段的使用。
- 健康检查直接返回简单 JSON，不使用业务响应封装，这是基础设施端点的明确例外。

这些差异应通过独立安全或实现任务修复；本文档只准确记录现状。

## 11. 规划能力

以下能力未形成当前可运行链路：

- Redis 缓存和分布式限流。
- 敏感词检查服务。
- 纠错投票、修改任务和消息通知。
- 论坛、问答和反馈完整接口。
- 结构化日志和集中监控。

规划能力落地时，必须更新需求基线、依赖清单、系统设计和对应测试，不能只增加模型、页面或权限码。
