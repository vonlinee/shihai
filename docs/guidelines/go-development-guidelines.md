# Go 开发规范

本文档约束识海后端的 Go 代码。项目目录、分层、API、数据库和权限规则见 [后端指南](backend-guidelines.md)。

## 1. 规则级别

- **必须**：可以通过编译、测试、静态检查或代码审查明确验证。
- **建议**：默认采用，但在现有代码模式或具体场景不适合时可以说明原因后调整。

## 2. 格式化与导入

- 修改过的 Go 文件必须执行 `gofmt`。
- 建议使用 `goimports` 整理导入，但不得为未修改文件制造大范围格式变化。
- 导入按标准库、第三方包、项目内包分组，组间保留空行。
- 禁止提交未使用的导入、变量或不可达代码。

```bash
cd backend
gofmt -w <changed-go-files>
go test ./...
```

## 3. 命名

- 包名使用简短的小写单词，不使用下划线和无意义缩写。
- 导出标识符使用 PascalCase，包内标识符使用 camelCase。
- `ID`、`URL`、`HTTP`、`JWT` 等常见缩写保持统一大小写，例如 `userID`、`ParseURL`、`HTTPClient`。
- 文件名使用小写和下划线，表达主要职责，例如 `poem_service.go`。
- 接口名称描述能力；只有语义自然的单方法接口才使用 `-er` 后缀。
- 避免包名与导出名称重复，例如优先使用 `repository.User`，不要使用 `repository.UserRepositoryModel`。

## 4. 函数与类型

- 函数应聚焦一个职责；长度只是评审信号，不设置机械行数上限。
- 参数较多且属于同一概念时，使用请求结构体或选项结构体，避免长参数列表。
- 零值有明确安全语义时优先使用零值；必须初始化的类型通过构造函数创建。
- 不为了“以后可能复用”提前导出类型或函数。
- 只有调用方确实需要替换实现或隔离依赖时才定义接口，接口通常由使用方所在包定义。

## 5. 注释

- 导出的包、类型、函数、方法和变量应有符合 Go Doc 风格的注释，首句以标识符名称开头。
- 包内代码只在业务意图、边界条件或实现原因不直观时添加注释。
- 注释解释“为什么”和约束条件，不逐行翻译代码。
- 不在源码注释中维护作者、创建时间、修改时间或修改历史；这些信息由 Git 记录。
- 不要求每个结构体字段都重复写与字段名相同的注释；字段业务含义不明确时必须说明。

## 6. 错误处理

- 所有返回的错误必须被处理或明确向上返回，禁止使用空白标识符静默忽略。
- 增加上下文时使用 `fmt.Errorf("...: %w", err)` 保留错误链。
- 调用方需要区分错误类型时，使用哨兵错误、自定义错误类型以及 `errors.Is`、`errors.As`，不要依赖错误文本比较。
- 错误信息使用小写开头且不以句号结尾，除非该文本直接面向用户。
- 业务代码禁止使用 `panic`。启动阶段遇到无法恢复的配置或依赖初始化错误时可以终止进程。
- 不向客户端返回数据库错误、文件路径、堆栈或内部实现细节。

```go
poem, err := repo.GetByID(ctx, poemID)
if err != nil {
    return nil, fmt.Errorf("get poem %d: %w", poemID, err)
}
```

## 7. Context 传递

- HTTP 请求触发的数据库、网络和长耗时操作应接收并传递 `context.Context`。
- `context.Context` 作为第一个参数，命名为 `ctx`，不存入结构体字段。
- Handler 从 `c.Request.Context()` 获取请求上下文。
- 不使用 `context.Background()` 绕过请求取消；只有启动任务或明确独立于请求的后台任务可以创建根 Context。
- 新增 Repository 方法时优先接收 Context，并使用 GORM 的 `WithContext(ctx)`。

现有未传递 Context 的方法可以按业务修改范围逐步迁移，不要求无关任务一次性重构全部调用链。

## 8. 并发

- 只有能够证明并发带来收益时才创建 goroutine。
- goroutine 必须有明确的结束条件、取消机制和错误处理方式。
- 不允许多个 goroutine 在没有同步措施时读写同一可变数据。
- 共享缓存或单例使用 `sync.Once`、互斥锁或其他明确同步机制。
- 不从请求处理器启动无法追踪、无法取消的后台任务。
- 通道由发送方或拥有其生命周期的一方关闭，接收方不随意关闭通道。

## 9. 数据与序列化

- 业务主键使用项目统一的 Snowflake `uint64` 类型。
- 返回给 JavaScript 的 Snowflake ID 必须在响应 DTO 中序列化为字符串。
- 请求 ID 使用项目统一解析类型，兼容字符串和必要的历史数字输入；不得在各 Handler 重复实现解析逻辑。
- 不直接把 GORM Model 当作外部响应契约。
- 时间、枚举和可空字段的 JSON 表达应在 DTO 中明确，不依赖调用方猜测零值含义。

## 10. 测试

- 测试文件与被测代码同目录，使用 `_test.go` 后缀。
- 新增或修复重要业务规则时，至少覆盖成功路径、关键失败路径和边界条件。
- Service 测试应隔离数据库依赖；Repository 测试可使用测试数据库或明确的数据库替身。
- Handler 测试使用 `httptest` 验证参数、状态码和响应契约。
- 测试名称应表达被测行为和场景；表驱动测试适合多个输入共享同一断言结构的情况。
- 测试不得依赖执行顺序、真实外部网络或开发者本机状态。

```bash
cd backend
go test ./...
go test ./internal/services/... -v
```

## 11. 依赖管理

- 新增依赖前确认标准库和现有依赖不能合理解决问题。
- 不引入只为少量辅助函数服务的大型依赖。
- 修改依赖后运行 `go mod tidy`，并检查 `go.mod`、`go.sum` 差异是否仅包含预期内容。
- 禁止直接编辑模块缓存或提交本地构建产物。
- 安全相关依赖应使用维护中的稳定版本，并在升级时运行完整后端测试。

## 12. 变更范围

- 优先沿用当前包和分层结构，不在普通功能任务中重建整个项目布局。
- 发现历史代码不符合本文档时，只修复与当前任务直接相关且风险可控的部分；大范围迁移应独立立项。
- 规范与代码现状冲突时，先确认是文档失真还是实现债务，并在变更说明中记录处理结果。
