# 识海古诗词学习平台需求设计

## 1. 文档定位

本文档定义识海平台的产品目标、当前需求基线和后续规划。它回答“系统应该提供什么能力”，不规定框架、目录、接口实现或数据库字段。

功能状态分为：

- **当前范围**：已有可调用的后端路由或完整管理流程，是维护和迭代时的现行基线。
- **部分实现**：只有页面、模型、权限码或其他局部结构，尚未形成完整业务链路。
- **后续规划**：尚未进入当前交付范围，不得按已实现能力对外说明。

实际架构和已知差异见 [系统设计文档](system-design.md)。

## 2. 产品目标

识海面向古诗词学习者和内容维护人员，提供诗词浏览、内容学习、评论互动和后台资源管理能力。产品设计优先保证：

- 诗词内容清晰、可检索、可持续维护。
- 普通用户可以完成基础学习和互动流程。
- 后台操作受角色与权限控制，并保留清晰的职责边界。
- 个人信息收集保持必要、透明和可控制。
- 规划功能不会被误认为已经交付。

## 3. 角色与权限

### 3.1 游客

游客无需登录即可浏览公开诗词、公告和公开评论。是否允许游客投票由接口策略决定；游客不能访问个人资料和后台管理功能。

### 3.2 普通用户

普通用户通过用户名和密码登录，可以管理自己的基础资料、发表评论、删除自己的评论，以及使用后续开放给普通用户的互动能力。

### 3.3 编辑

编辑负责诗词、作者、朝代、作品集、诗词标注和相关内容的维护。编辑只能获得完成内容维护所需的权限，不自动继承管理员权限。

### 3.4 审核员

审核员负责评论或纠错等审核工作。审核权限通过独立 RBAC 权限码授予，不自动获得用户管理、角色管理或系统配置权限。

### 3.5 管理员

管理员负责账号、角色、权限和全局后台资源管理。高权限操作必须由后端鉴权和授权，不能只依赖前端隐藏菜单。

用户登录时只提交身份凭证。角色和权限由服务端根据账号关联关系确定，客户端不得通过“选择角色”改变身份。

## 4. 当前功能范围

### 4.1 账号与身份

- 用户注册和登录。
- 登录用户查看、修改个人资料和修改密码。
- 管理员查看、创建和删除用户。
- 管理员维护角色、权限以及用户角色关联。

注册的必要字段为用户名和密码。昵称或姓名、头像等展示资料可以选填或按现有接口约束填写。身份证号、年龄和手机号不属于产品必要信息，不应作为注册前提；若未来用于实名认证或账号找回，必须先明确业务必要性、授权方式、保存期限和删除机制。

### 4.2 诗词学习

- 浏览诗词列表、随机诗词和诗词详情。
- 按朝代、诗人和体裁获取筛选数据。
- 查看正文、译文、赏析、注释、音频和封面等已有内容。
- 对诗词执行当前接口支持的点赞操作。

### 4.3 评论互动

- 公开查看评论列表。
- 登录用户发表评论、回复和删除自己的评论。
- 登录用户或游客按当前接口策略对评论点赞或点踩。
- 后台按权限查看评论管理列表。

同一主体对同一评论只能保留一种投票状态；重复相同操作用于取消，切换操作用于变更投票类型。服务端必须负责去重和计数一致性。

### 4.4 公告

- 公开查看公告列表和详情。
- 后台按权限创建、修改和删除公告。

### 4.5 后台内容管理

- 维护诗词、朝代、诗人和作品集。
- 维护诗词正文范围标注。
- 对标题、正文、译文、赏析、注释和诗词标注文本进行简繁转换辅助编辑。
- 管理用户、角色、权限和用户角色关系。

简繁转换只改变编辑中的文本值，不自动保存；保存仍走原有诗词或标注接口，并受对应更新权限控制。

## 5. 部分实现

以下能力已存在页面、模型或权限定义，但当前仓库没有完整的 Handler、Service、Repository 和路由闭环：

- 论坛发帖、回复和后台管理。
- 诗词问答、答题和答题记录。
- 纠错申请、投票、修改任务和通知。
- 在线反馈。

这些结构可以用于后续开发，但不能仅凭页面路由、数据模型或权限码认定功能已经可用。新增完整链路前，应重新确认业务规则、接口契约和测试范围。

## 6. 关键业务规则

### 6.1 登录与授权

1. 客户端提交用户名和密码。
2. 服务端验证账号状态和密码。
3. 服务端签发令牌，并根据用户角色聚合权限。
4. 前端可根据权限调整导航和按钮展示。
5. 后端对每个受保护接口再次执行认证和权限校验。

### 6.2 游客标识

- 游客公开标识应由服务端生成随机、不透明的值，不直接展示 IP 或浏览器指纹。
- IP 可以用于限流、滥用检测和短期安全审计，但应限制访问范围和保存期限。
- 对 IP 做普通哈希不能自动满足匿名化要求；不得将其表述为完整隐私保护方案。
- 同一游客的去重策略必须允许轮换和失效，不能成为无限期跟踪标识。

### 6.3 纠错流程

纠错功能进入完整实现前，必须同时确定以下规则：

1. 可纠错字段和提交证据要求。
2. 审核员的一人一票和重复提交约束。
3. 法定人数、投票截止时间、通过阈值和平票处理方式。
4. 审核通过后的修改责任人和二次校验方式。
5. 撤销、终止、超时和异常恢复规则。
6. 申请人可见的状态及通知渠道。

这些值应作为同一组业务配置管理，不能只写“超过 50%”而不定义分母和截止条件。

## 7. 数据来源与内容合规

- 导入开源数据前必须核验许可证、允许用途、署名要求和再分发条件，并记录来源版本。
- 网络采集必须遵守来源网站条款、版权要求和 robots 规则。可公开访问不等于允许批量采集或商业使用。
- 人工录入内容应记录来源和维护责任，避免重复或无法追溯的内容。
- 用户提交的纠错依据和文本同样需要进行内容合规与敏感信息检查。

## 8. 数据与隐私

- 只收集完成功能所需的最少数据。
- 密码必须使用单向密码哈希保存，任何响应和日志都不得返回密码。
- 令牌、数据库凭证和其他密钥不得写入日志或提交到版本库。
- 个人资料应具备明确的访问控制；后台批量查询和导出需要独立权限。
- 新增手机号、邮箱、实名信息或设备标识前，必须说明用途、是否必填、保存期限、删除方式和可访问角色。

## 9. 非功能要求

### 9.1 可用性

- 常用浏览、编辑和后台管理流程应有明确的加载、空数据、失败和提交中状态。
- 破坏性操作需要二次确认，重复提交必须被阻止或做到幂等。
- 支持当前项目明确维护的主流桌面浏览器；扩大移动端或平板范围时应增加对应验收视口。

### 9.2 性能

性能目标只有同时记录以下条件时才能作为验收标准：

- 测试环境和服务资源。
- 数据规模和测试数据分布。
- 被测接口或用户流程。
- 并发模型、持续时间和预热方式。
- P95、P99 或其他统计口径。

“同时在线 1000 用户”或“响应时间不超过 1 秒”等缺少上述条件的数字只能作为产品目标，不能直接作为通过结论。

### 9.3 安全与可靠性

- 认证、授权、输入校验和数据访问控制必须在后端执行。
- 多表写入需要明确事务边界，失败时不得留下部分成功状态。
- 对评论、登录和其他可滥用接口实施限流或等效防护。
- 重要业务规则应通过自动化测试覆盖；故障信息不得向客户端暴露数据库和内部堆栈细节。

## 10. 后续规划

以下能力尚未作为当前交付承诺：

- 论坛和问答完整业务链路。
- 纠错投票、任务分配和消息通知。
- 收藏、积分、打卡和排行榜。
- Redis 热点缓存、敏感词服务和实时推送。

规划项进入开发前，应先更新本需求基线，再同步更新系统设计和涉及端的开发规范。
